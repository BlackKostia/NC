## 2. Методика вимірювання

Для виключення суб'єктивних оцінок замір проводився автоматизовано через реальний псевдотермінал (PTY) у рівних умовах для всіх TUI-менеджерів:

1. **Розмір термінала:** `40×120`, `TERM=xterm-256color`.
2. **Чесне визначення готовності (без перебору всього каталогу до старту):**
   - перед запуском скрипт бере лише перші `25` записів через `os.scandir()` (один буфер `getdents64`) та будує універсальний шаблон розширення `[A-Za-z0-9_-]{3,}\.dat`;
   - фіксується час від `Popen` до появи **першого кадру** в PTY, що містить будь-який відрендерений `.dat`-файл (працює однаково чесно і для потокового рендеру, і для менеджерів із попереднім алфавітним сортуванням).
3. **Кількість прогонів:** `1` прогрів (warmup) + `3` вимірюваних прогони.
4. **Таймаут і захист від зависання:** `60.0` секунд на прогін; при перевищенні `60 с` дерево процесів примусово завершується (`SIGTERM` → `SIGKILL`), а подальші прогони для цього менеджера пропускаються.
5. **Пам'ять (Peak RSS):** зчитується через `/proc/<pid>/status` (`VmHWM`/`VmRSS`) та `os.wait4(..., ru_maxrss)`.

Команда запуску:
```bash
python3 scripts/bench_compare.py --dir /home/chessplayer/duop_perf_20m --runs 3 --warmup 1 --timeout 60
```

## 4. Інженерний аналіз результатів

1. **Чому конкуренти перевищили 60 секунд:**
   Класичні та сучасні TUI-менеджери (`mc`, `yazi`, `lf`, `nnn`, `ranger`, `vifm`) перед малюванням першого кадру намагаються **повністю вичитати каталог у пам'ять** (часто з викликами `stat`/`lstat` та побудовою структур для всього списку й повним сортуванням). На каталозі масштабу `4 798 976` файлів це перетворюється на тривале блокування старту (> 60 с) та значне навантаження на пам'ять.
2. **Чому `duop` відкриває каталог за ~26 мс і витрачає 15.43 MiB:**
   - **Потоковий рендер ([dir_model_stream.s](../src/fs/dir_model_stream.s)):** `duop` не блокує інтерфейс до завершення повного обходу, а формує перший видимий екран одразу після початкової порції `getdents64`.
   - **Компактна модель пам'яті:** `32`-байтовий `FileEntry`, суцільний `name_pool`, `4`-байтовий масив індексів `order[]` і ледачий `d_type` без зайвих `stat` для кожного запису.
   - **Zero-`libc` старт:** відсутність динамічного лінкера, рантайму мови чи важких бібліотек дає миттєвий запуск процесу.
3. **Вплив міграції на freestanding C23:**
   Оскільки алгоритмічні рішення, потоковий конвеєр та асемблерний PAL (`src/os/` — `getdents64`, `io_uring`, SIMD) зберігаються, перенесення прикладних шарів із `.s` на freestanding C23 не змінює порядок швидкодії. Для контролю відсутності регресій при міграції `src/fs/dir_model*.s` і `src/fs/dir_sort*.s` слід використовувати `scripts/bench_compare.py` як регресійний гейт.
